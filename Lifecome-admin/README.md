# LifeCome Live — Operations console

The internal admin app for [LifeCome Live](../README.md) staff: the blueprint's "operations
console" (§1.1) — admin, payer ops, support, audit and content tooling over
[`Lifecome-backend`](../Lifecome-backend)'s API. It is not patient-facing (that's
[`Lifecome-web`](../Lifecome-web) and [`Lifecome-mobile`](../Lifecome-mobile)) and it is not the
clinician-facing **provider workspace** the blueprint describes separately (§1.1) — that's a
different app, for doctors and care coordinators, not built here.

## Status

**Scaffolded, with a handful of screens built for real against demo data**, the same way
`Lifecome-mobile` started: every route the blueprint's personas need has a page, the shared shell
(sidebar, topbar, design tokens) is real, and **Dashboard**, **Patients** (list + detail),
**Bookings** and **Payments** are fully built as the reference pattern — a real `DataTable`,
real charts, real detail layouts, backed by demo data instead of the live API. Every other section
renders a labelled placeholder naming the backend module it will read from. See
[Demo data](#demo-data) for why, and [Known gap: admin auth](#known-gap-admin-auth) for the one
thing blocking any of this from talking to a real signed-in session.

## Who this is for

The blueprint's operations personas (§2.3) — this console is where they work:

| Role | What they do here |
|---|---|
| Platform administrator | Configuration, content, roles, integrations, monitoring |
| Clinical administrator | Clinician management, governance, escalation |
| HMO operations | Eligibility/authorisation review, reconciliation |
| Support agent | Account and booking support, with restricted clinical-data access |
| (Audit) | Everyone above is themselves audited — see the Audit log section |

Doctors and care coordinators are **not** users of this app — they get the separate provider
workspace the blueprint describes, not yet built.

## Stack

| Concern | Choice | Why |
|---|---|---|
| Framework | [Next.js](https://nextjs.org) 16 (App Router), React 19, TypeScript | Same stack as `Lifecome-web` — one set of conventions across the two web apps |
| Styling | Tailwind CSS v4 | Same design tokens as `Lifecome-web` (see [Design tokens](#design-tokens)) |
| Components | [Radix UI](https://radix-ui.com) primitives + hand-rolled styling (the shadcn/ui pattern) | Accessible unstyled primitives (dialog, select, popover, toast...) without a component library's opinionated CSS to fight |
| Data tables | [TanStack Table](https://tanstack.com/table) | Headless — sorting, filtering and pagination logic without dictating markup, so every list page shares one `DataTable` |
| Server state | [TanStack Query](https://tanstack.com/query) | Caching, refetch-on-focus and mutation state for calls to the backend, once real calls exist |
| Charts | [Recharts](https://recharts.org) | Composable SVG charts for the dashboard's volume/mix views |
| Forms | React Hook Form + Zod | Same validation library as the backend (`nestjs-zod`) — schemas can eventually be shared |
| API client | Hand-rolled `fetch` wrapper (`lib/api/client.ts`) over types generated by `openapi-typescript` from the backend's published OpenAPI contract | The backend's README says its Swagger docs are "published... for the web and mobile clients to codegen from" — this is that, for the console |

## Getting started

You need Node.js 20+ and a running `Lifecome-backend` (see its README) for anything beyond the
demo-data pages to eventually work.

```bash
cp .env.example .env.local   # point NEXT_PUBLIC_API_URL at your backend
npm install
npm run dev                  # http://localhost:3000 by default
```

| Command | What it does |
|---|---|
| `npm run dev` | Start the dev server (Turbopack) |
| `npm run build` | Production build |
| `npm run start` | Run the built app |
| `npm run lint` | ESLint |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run generate:api` | Regenerate `src/lib/api/generated/schema.d.ts` from the backend's live OpenAPI contract (`$NEXT_PUBLIC_API_URL/docs-json`) — run this whenever the backend's API shape changes |

## Demo data

`Dashboard`, `Patients`, `Bookings` and `Payments` render real, interactive UI backed by literal
arrays in `src/lib/demo/*.ts` instead of `fetch` calls — the same trade-off
`Lifecome-mobile`'s `FakeAuthRepository` and friends make, for the same reason: the backend's REST
API exists and works, but this app's admin-specific concerns (an aggregate dashboard endpoint,
pagination/filtering query params tuned for a staff console, and — the bigger blocker — any way to
authenticate as staff at all) don't exist yet. Building against demo data now means the console's
UI, its `DataTable`, and its per-module patterns are all settled and reviewable today, and swapping
each `lib/demo/*.ts` array for a `useQuery` in the matching `features/*/api.ts` is a contained,
mechanical change later — nothing in `components/` or `app/` should need to change when it happens.

The demo people (Ngozi Adeyemi, Ada Okonkwo, Dr. Adaeze Okonkwo, Reliance HMO, ...) are the same
ones used throughout `Lifecome-mobile`'s fake repositories, so a screenshot from either app reads
as the same platform.

## Known gap: admin auth

`Lifecome-backend`'s `identity` module is patient-only today — there is no staff/role concept, no
admin login endpoint, and no way to tell a platform administrator apart from a support agent at the
API layer. The blueprint calls for that distinction (§2.3: platform administrator, clinical
administrator, HMO operations, support agent are separate roles with separate permissions), but it
doesn't exist yet on the backend.

Consequences, all marked with `TODO`/doc comments at the relevant file:

- `/login` renders a real-looking form with a disabled submit button.
- `lib/auth/session.ts` and `lib/auth/guards.ts` are empty placeholders.
- `(console)/layout.tsx` has no auth check — every route is reachable without signing in.
- `lib/api/client.ts` sends `credentials: "include"` but attaches no auth header.

None of this can be finished on the console's side alone. It needs, on `Lifecome-backend`:

1. A `role` column (or a separate `staff` table) distinguishing the personas in §2.3.
2. A staff login endpoint (or reusing `identity`'s existing one with a role check).
3. Route guards on every admin-facing endpoint this console will call.

## Design tokens

The brand palette, spacing and radii in `src/app/globals.css` are copied by hand from
`Lifecome-web/src/app/globals.css` rather than shared as a package — the two apps started from
the same file and are expected to drift only in the console's dark-mode-by-default choice (see the
comment in `globals.css`). If a third web app joins this workspace, that's the point to extract a
shared `@lifecome/tokens` package instead of copying a third time.

## What's next

Beyond the modules already listed as placeholders, roughly in the order they unblock the most:

1. Staff auth on the backend (see [Known gap: admin auth](#known-gap-admin-auth)) — nothing else
   here becomes real without it.
2. `npm run generate:api` against a running backend, then wire `Patients`, `Bookings` and
   `Payments` to real `useQuery` calls as the first migration off demo data.
3. Build out `Providers`, `Payers`, `Audit log` and `Consent` next — the modules the blueprint's
   governance requirements (§2.2, §7) lean on most.
4. A command palette (`cmdk` is already a dependency) for cross-module search from the topbar.
5. The `components/ui/` folder is still empty — add Radix-based primitives (dialog, select,
   dropdown, toast) as each is actually needed, rather than generating the full shadcn/ui set
   upfront.
